# `astute_call_logger` — Table Reference

## Purpose

`astute_call_logger` is a Postgres table that records every Astute portfolio lookup made
by the service, storing the raw XML responses from **two data sources side by side** —
Oracle (the existing source) and Data Platform (the newer replacement). This makes it
possible to compare the two sources offline without replaying live calls.

The comparison scripts ([`compare_xml.py`](./compare_xml.md) and
[`compare_json.py`](./compare_json.md)) read directly from this table.

---

## Schema

```sql
CREATE TABLE astute_call_logger (
    id                      SERIAL PRIMARY KEY,
    id_number               VARCHAR(255),   -- SA ID number of the investor
    gemstone                TEXT,           -- legacy Gemstone XML response (xml)
    oracle_mapping          TEXT,           -- Oracle XML response            (xml)
    dataplatform_mapping    TEXT,           -- Data Platform XML response     (xml)
    gemstone_duration       VARCHAR(255),   -- how long the Gemstone call took
    oracle_mapping_duration VARCHAR(255),   -- how long the Oracle call took
    call_method             VARCHAR(255),   -- which SOAP/REST method triggered the call
    created_at              TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

> The `TEXT` columns are annotated `columnDefinition = "xml"` in the JPA entity so
> Hibernate knows the Postgres column type — but the values are plain XML strings.

## Key Columns

### `oracle_mapping`

The **JAXB-serialised XML response** from the Oracle data source for the given
`id_number`.

- Source: `AstuteOracleRepository` → `AstuteMapper.mapToReturnType()` → XML string
- Contains the full Astute portfolio object (Parties, Holdings, etc.) as returned by
  Oracle, or a SOAP Fault XML if no active contract was found
- If Oracle short-circuits (e.g. `errorNumber=2102`), this column stores the fault
  message generated by `DefaultAstuteCallLoggerService.generateFaultMessage()`
- Stored by: `DefaultAstuteCallLoggerService.logAstute()` at `DefaultAstuteCallLoggerService.java:184`

### `dataplatform_mapping`

The XML response from the Data Platform for the same `id_number`. It is the same
JAXB-serialised Astute portfolio object, but sourced from the newer Data Platform
integration (`DataPlatformRepositoryBean`).

- Source: `DataPlatformRepositoryBean` → mapped via `AstuteMapper` → serialised to XML string
- Stored by: `DefaultAstuteCallLoggerService.logAstute()` at `DefaultAstuteCallLoggerService.java:185`
- Added later via migration: `V20250929190148__dataplatform_column.sql`
- `NULL` for rows written before the Data Platform integration was added

## How rows are written

`DefaultAstuteCallLoggerService.logAstute()` (`DefaultAstuteCallLoggerService.java:177`)
is the single write path:

```java
public void logAstute(String idNumber, String gemstoneResponse, String dbXMLString,
                      String DataPlatformResponse, String gemstoneCallDuration,
                      String oracleDuration, String method, AstuteData astuteData) {
    AstuteCallLogger callLogger = new AstuteCallLogger();
    callLogger.setIdNumber(idNumber);
    callLogger.setGemstone(gemstoneResponse);
    callLogger.setOracleMapping(dbXMLString);          // → oracle_mapping
    callLogger.setDataPlatform(DataPlatformResponse);  // → dataplatform_mapping
    callLogger.setGemstoneDuration(gemstoneCallDuration);
    callLogger.setOracleMappingDuration(oracleDuration);
    callLogger.setCreatedAt(new Timestamp(new Date().getTime()));
    callLogger.setCallMethod(method);
    astuteCallLoggerRepository.save(callLogger);
}
```

Writes are **async** — triggered via `CompletableFuture.runAsync` so they do not block
the live SOAP/REST response.

```java
@Entity
```

## Querying the table

Fetch the latest row per investor for comparison (used by both scripts and the DBeaver
export):

```sql
SELECT DISTINCT ON (id_number)
    id_number,
    oracle_mapping,
    dataplatform_mapping
FROM astute_call_logger
ORDER BY id_number, created_at DESC;
```

Limit to today only:

```sql
SELECT DISTINCT ON (id_number)
    id_number,
    oracle_mapping,
    dataplatform_mapping
FROM astute_call_logger
WHERE created_at >= CURRENT_DATE
ORDER BY id_number, created_at DESC;
```

> The DB defaults for both scripts already target `astute-logging-pre`. Supply the
> password via `PGPASSWORD` or `--password`. Queries are **read-only**.

## Why the scripts exist

The `compare_json.py` and `compare_xml.py` scripts read the `oracle_mapping` and
`dataplatform_mapping` columns and compare them to find **real business data differences**
between Oracle and Data Platform responses — the goal being to validate that the Data
Platform is a safe replacement for Oracle.

| Script | Approach |
|---|---|
| [`compare_xml.py`](./compare_xml.md) | Compares the two XML payloads directly on the XML tree (canonicalise + flatten). Faster. |
| [`compare_json.py`](./compare_json.md) | Converts each side's XML to a JSON object first, then diffs the JSON objects. Mirrors the manual "XML → JSON → compare" method. |

Both scripts strip cosmetic noise (element ordering, whitespace, synthetic cross-reference
ids) so only genuine data differences are reported. See [`README.md`](./README.md) for
the full comparison and quick-start commands.

## Findings — 15 Jun 2026 run (`astute_call_logger_202606150949.csv`)

### Approach

`compare_json.py` was run against a DBeaver export of the `astute_call_logger` table
(1,651 IDs, latest row per ID). The script:

1. Reads `oracle_mapping` and `dataplatform_mapping` for each ID.
2. Converts each XML payload into a nested JSON object (namespaces stripped, repeated
   elements become lists).
3. Diffs the two JSON objects field by field — matching repeated entities (Parties,
   Holdings) by business key (`FullName`, `*Number`/`*Key`), not by position, so
   reordering does not create false differences.
4. Classifies each ID and writes field-level diffs to CSV.

Command used:

```bash
python3 compare_json.py \
    --csv astute_call_logger_202606150949.csv \
    --out-dir ./out \
    --dump-json ./out/json
```

---

### Results

#### ID classification (1,651 total)

| Classification | Count | What it means |
|---|---|---|
| `MATCH` | 0 | No IDs were identical across both sources |
| `MISMATCH_REAL` | 51 | Genuine field-level differences found |
| `NO_DP_DATA` | 60 | Oracle had data; Data Platform returned nothing or a fault |
| `NO_ORACLE_DATA` | 847 | Data Platform had data; Oracle returned nothing or a fault |
| `BOTH_EMPTY` | 693 | Neither source returned data for the ID |

> **`NO_ORACLE_DATA` (847 IDs — 51% of the dataset)** is the most significant finding.
> Over half the IDs have a valid Data Platform response but Oracle is returning faults or
> empty results. This needs to be investigated — either Oracle is silently failing for
> these contracts, or these are genuinely Data Platform-only records that have never
> existed in Oracle.

#### Field diffs across the 51 real mismatches

| Kind | Count | Meaning |
|---|---|---|
| `oracle_only` | 228 | Field present in Oracle, **missing in Data Platform** |
| `dp_only` | 68 | Field present in Data Platform, **missing in Oracle** |
| `value_diff` | 3 | Both sides have the field but the values differ |

The dominant gap is `oracle_only` (228) — Data Platform is missing data that Oracle
has, not the other way around.

#### Top diverging fields

| Occurrences | Field path | Notes |
|---|---|---|
| 51 | `return/result/OLifE/Holding` | All 51 mismatched IDs are missing Holding data on one side — systematic mapping gap |
| 51 | `return/result/OLifE/Relation` | Same 51 IDs missing Relation data — likely the same root cause |
| 5 | `return/result/OLifE/Party[TRANSNET RETIREMENT FUND]` | Organisation party missing on one side for 5 IDs |
| 2 | `return/result/OLifE/Party[Siwela, W]` / `Party[Siwela, Willy]` | Same person, different name formats — matching key mismatch |
| 1 each | Various `Party[...]` entries with inverted name formats | `Firstname Lastname` vs `Lastname, Firstname` — same issue |

---

### Interpretation

**1. `Holding` and `Relation` gap (51 IDs)**

Every real mismatch includes missing `Holding` and `Relation` nodes. This is a
systematic mapping defect — one source is not populating these structures for the
same contracts. Cross-reference against `astute-oracle-mapping.md` to identify which
mapping rule is absent.

**2. Duplicate party name keys (multiple IDs)**

The same investor appears twice in the diff under two different keys because the name
format differs between sources — e.g. `Siwela, Willy` (Oracle) vs `Siwela, W` (Data
Platform), or `Kok, Hemanus Johannes Wessels` vs `Hemanus Johannes Wessels Kok`. The
script matches list items by `FullName`, so a format difference causes the entity to
show as missing on each side rather than as a single `value_diff`. These are likely
**not** real data gaps — they are the same person recorded with inconsistent name
formatting.

**3. `NO_ORACLE_DATA` (847 IDs)**

Requires separate investigation. Possible causes:
- Oracle is returning `errorNumber=2102` (no active contract) for contracts that Data
  Platform considers active.
- These IDs were migrated to Data Platform and decommissioned in Oracle.
- Oracle is experiencing intermittent faults that were not retried.

---

### Next steps

1. **Investigate `NO_ORACLE_DATA` (847)** — run Query 3 against a sample of these IDs
   to confirm whether Oracle is returning a fault or genuinely has no record.
2. **Fix the `Holding`/`Relation` mapping gap** — identify the missing mapping rule
   and raise a defect against the Data Platform integration.
3. **Normalise party name formatting** — align `FullName` format between Oracle and
   Data Platform so the matching key resolves correctly and false "missing entity"
   reports are eliminated.
4. **Re-run after fixes** — use the same command against a fresh export to measure
   improvement.
